# 0. Governing decision

The DIAL Brand Pack is a **DIAL Identity and Product-Expression authority package**.

It is not a second frontend design system and it is not a parallel VEKL.

Its job is to answer:

- what makes a DIAL product recognizably DIAL;
- how DIAL identity should behave across very different product contexts;
- which brand assets, primitives and expressive principles are stable;
- which parts of brand expression are contextual and may vary;
- which brand intelligence should be projected into each development stage;
- how brand information enters Product Experience, VEKL-guided design, Stitch and DDE without taking over their responsibilities;
- how accepted frontend work may teach reusable design knowledge without silently mutating brand canon.

The key operating principle is:

> **Brand Pack supplies identity and expressive intelligence.  
> Project Truth supplies product truth.  
> Screen Registry × Feature Graph supplies screen responsibility.  
> VEKL supplies qualified development/design knowledge.  
> Stitch authors visual and interaction solutions inside the envelope.  
> Visual/Experience Authority freezes approved outcomes.  
> DDE productionizes without redesign.**

Reverse authority flow is forbidden.

# 3. Core DIAL identity

## 3.1 Identity proposition

DIAL should feel like one coherent environment of trusted solutions rather than a collage of unrelated vertical brands.

The visual identity must communicate:

- confidence;
- clarity;
- usefulness;
- trust;
- operational competence;
- premium but human presentation;
- modern product quality;
- restrained sophistication;
- contextual depth rather than decoration.

## 3.2 Canonical colour law

The owner-directed colour law is:

> **White creates space.  
> Black creates structure.  
> Orange creates attention.**

Supporting law:

> **DIAL is not an orange UI. It is a premium neutral interface whose identity is revealed through precise orange interventions.**

Hierarchy must be created with composition, type, scale, spacing, imagery and contrast **before** additional colour is used.

When uncertain, remove orange rather than add it.

## 3.3 Brand composition signature

A recurring DIAL composition should tend toward:

> **light field → dark structural anchor → orange spark**

This is not a mandatory screen template. It is a brand-recognition grammar.

The grammar may be inverted in dark mode or operational contexts, but the relative role of the three colours remains stable:

- neutral/light = environment and breathing room;
- black/charcoal = structure and authority;
- orange = selective attention and brand recognition.

# 4. Colour system

## 4.1 Colour responsibility

A normal DIAL product screen should usually read as predominantly neutral with strong dark structure and sparse orange emphasis.

Recommended design-intent ranges for ordinary product UI:

- neutral / white / warm-white: roughly 70–80%;
- black / charcoal / graphite: roughly 15–25%;
- DIAL orange: roughly 3–7%.

These are **critic heuristics**, not hard pixel quotas. Exceptional brand/acquisition campaigns may intentionally exceed them when approved by the applicable design zone.

## 4.2 Orange jobs

Strong orange should ordinarily perform one of five jobs:

1. primary intent;
2. active selection;
3. progress / directional emphasis;
4. deliberate brand anchor;
5. controlled promotional focus.

Orange should not be used merely because an element needs decoration.

## 4.3 Initial Rev 1 palette seeds

The following values are initial Brand Pack seed tokens and require owner visual approval before promotion to immutable canonical colour values:

| Token | Seed value | Intent |
|---|---|---|
| `brand.dial.orange.core` | `#F36A36` | brand accent, icons, active markers, visual anchors |
| `brand.dial.orange.action` | `#C84E1A` | solid orange action surface where white text is required |
| `brand.dial.orange.soft` | `#FFF0E8` | low-emphasis selected/promotional tint |
| `brand.dial.black` | `#0D0D0D` | primary dark |
| `brand.dial.charcoal` | `#171717` | contrast panels / elevated dark surfaces |
| `brand.dial.graphite` | `#2A2928` | secondary dark |
| `brand.dial.canvas` | `#FAF9F7` | warm neutral canvas |
| `brand.dial.surface.soft` | `#F4F2EF` | grouped secondary surface |
| `brand.dial.white` | `#FFFFFF` | elevated/clean surfaces |
| `brand.dial.border` | `#E5E2DE` | quiet separators |
| `brand.dial.text.muted` | `#77736F` | secondary copy |

Accessibility note: the core orange seed is not suitable for small white text by default. The darker action-orange seed is intended for cases where a solid orange action must carry white text. Final tokens must be certified under the normal accessibility pipeline.

## 4.4 Semantic colours remain separate

Brand orange does not replace semantic status colours.

- green: success / healthy / completed / available;
- amber: warning / attention;
- red: failure / destructive / critical error;
- blue/cyan: informational/system state where appropriate;
- orange: DIAL identity / active intent / selected focus.

A delivered order should not become orange merely because DIAL is orange.

## 4.5 Orange anti-patterns

Reject ordinary UI that:

- uses orange as a whole-screen background without a campaign-level reason;
- makes every action orange;
- makes inactive icons orange;
- repeats orange borders around ordinary cards;
- stacks multiple adjacent orange panels;
- uses orange for warnings/errors that should be semantic colours;
- uses orange to compensate for weak hierarchy;
- combines a strongly orange hero, strongly orange CTA and strongly orange navigation action without a deliberate exceptional composition.

# 5. Typography intelligence

The Brand Pack defines **character and hierarchy intelligence**, while renderer-specific type implementation remains in the frontend design system.

DIAL typography should be:

- clear;
- restrained;
- compact enough for operational surfaces;
- spacious enough for consumer discovery;
- confident rather than ornamental;
- readable under dynamic type scaling;
- compatible with multilingual/localization requirements.

Recommended identity direction:

- display/marketing: a modern geometric/humanist sans with confident mass;
- product UI: a highly legible sans optimized for dense interface use;
- numeric/operational contexts: tabular numerals where helpful.

The initial suggested pairing is **Manrope-like display character + Inter-like UI character**, but exact font-family adoption remains a separate asset/licensing/implementation decision.

Brand typography should guide:

- relative hierarchy;
- weight contrast;
- rhythm;
- editorial composition;
- micro-label use;
- uppercase tracking for contextual labels where appropriate.

It must not hard-code a single type scale across every screen class.

# 6. Spatial, geometry and depth intelligence

## 6.1 Geometry character

DIAL should use soft, modern geometry without becoming toy-like.

Brand tendencies:

- calm rounded rectangles;
- controlled pill shapes for chips/toggles;
- circular icon controls only where affordance benefits;
- generous but not wasteful internal spacing;
- alignment precision;
- subtle borders;
- shadows used for hierarchy, not decoration.

## 6.2 Density intelligence

Density comes from the Product Design Profile and screen role.

Examples already represented in the frontend profile registry:

- Groceries / Laundry / Van: comfortable;
- Logistics / Fleet / Corporate: compact;
- Control / Platform / GMPC / DKRF: operational;
- most consumer product modules: standard.

The Brand Pack must **not override those density decisions globally**.

## 6.3 Depth

Preferred depth order:

1. spacing and tonal separation;
2. border;
3. restrained shadow;
4. bounded glass/refraction when semantically justified;
5. dimensional 3D only where it improves understanding or deliberate premium storytelling.

Decorative depth on every surface is an anti-pattern.

# 7. Imagery, photography, illustration and 3D intelligence

## 7.1 Shared visual formula

A useful DIAL media formula is:

> **neutral environment + credible real object/person/context + dark structural anchor + one deliberate orange intervention**

This is guidance, not a mandatory art template.

## 7.2 Photography principles

Photography should feel:

- real;
- competent;
- locally plausible;
- useful to product understanding;
- naturally lit unless a cinematic treatment is justified;
- uncluttered enough to coexist with UI;
- free of invented product capabilities or unsafe practices.

## 7.3 Product-imagery pipeline

Commerce products should support professional asset preparation:

- capture / upload;
- background removal;
- crop/straighten;
- lighting/contrast normalization;
- de-noise/sharpen;
- perspective correction where justified;
- shadow/contact grounding;
- multiple aspect-ratio derivatives;
- web/app optimized outputs;
- provenance and original preservation.

The Brand Pack defines the desired visual quality. The actual image-processing capability remains a product/tool integration governed elsewhere.

## 7.4 3D and technical imagery

Spare, Vehicle Hub, technical services and selected premium pages may use:

- real product photography;
- CGI;
- exploded diagrams;
- line-to-object transitions;
- hotspot interaction;
- spatial inspection;
- vehicle-to-component transitions.

3D is justified when spatial relation, part understanding or premium product storytelling materially benefits.

It is not a requirement for every DIAL surface.

# 8. Interaction & Motion Intelligence

This section is deliberately **additive** to the existing interaction/motion design stage.

It does **not** define a closed animation library and does not reduce the design provider to preset effects.

## 8.1 Purpose

The Brand Pack supplies:

- motion character;
- temporal brand qualities;
- contextual opportunities;
- anti-character;
- continuity principles;
- product-specific physical metaphors;
- emotional pacing;
- feedback personality.

The `STITCH_INTERACTION_MOTION_ENRICHMENT` stage remains responsible for determining:

- actual gestures;
- advanced components;
- transition mechanics;
- motion timing;
- scroll behavior;
- gesture maps;
- `InteractionIntentMap`;
- `MotionSpec`;
- reduced-motion behavior;
- whether `NO_EFFECT_NEEDED` is the correct result.

## 8.2 DIAL motion character

Preferred characteristics:

- confident;
- immediate;
- physically coherent;
- purposeful;
- premium but not showy;
- causally understandable;
- responsive to user intent;
- continuity-preserving;
- capable of becoming quiet in safety/transactional contexts.

Avoid:

- decorative bouncing;
- endless floating;
- motion without cause/effect;
- attention competition;
- forced scroll theatre;
- novelty transitions that obscure state;
- animation that delays task completion;
- motion as a substitute for missing information architecture.

## 8.3 Product-specific opportunity intelligence

### Spare / Vehicle Hub
Potential opportunities:

- vehicle-to-component continuity;
- exploded assembly relationships;
- part inspection;
- focus/zoom progression;
- selected-vehicle context transitions;
- fitment-confirmation emphasis.

### Groceries
Potential opportunities:

- category continuity;
- basket response;
- quantity adjustment feedback;
- substitution decision clarity;
- fulfilment progression;
- calm merchandising motion.

### Logistics / Delivery
Potential opportunities:

- route continuity;
- custody handoff;
- position/progress change;
- pickup → transit → arrival continuity;
- map-to-card relationship;
- proof-of-delivery completion.

### Tech / Projects
Potential opportunities:

- request → diagnosis/quote → scheduled work → evidence → completion continuity;
- expandable evidence;
- job-state transitions;
- approval feedback.

### Laundry
Potential opportunities:

- pickup/custody progression;
- garment/item grouping;
- intake → processing → QC → return continuity.

### Care
Potential opportunities:

- entitlement reveal;
- covered-asset context;
- usage/limit comprehension;
- calm premium transitions.

### Health
Potential opportunities must be more conservative:

- continuity between care tasks;
- queue/appointment state;
- consent clarity;

Motion must never trivialize clinical/safety significance.

### Operational / provider surfaces
Prioritize:

- cause/effect;
- task completion;
- status change;
- error prevention;
- offline/sync clarity.

Cinema is subordinate to throughput and correctness.

## 8.4 Motion zone relationship

The existing Premium Cinematic Web Standard remains superior for intensity:

- Zone A brand/acquisition: high ceiling;
- Zone B discovery/browse/profile: medium ceiling;
- Zone C booking/quote/checkout/payment: low ceiling;
- Zone D HIRA/PPE/LOTO/SOP/job/admin: minimal ceiling.

Brand motion intelligence enriches the creative solution **inside** that ceiling.

# 9. Sound and haptic intelligence

Where platform capability exists, sound/haptics may reinforce:

- confirmation;
- completion;
- selection;
- drag/drop or scan;
- safety-critical acknowledgement;
- urgent owner attention.

Rules:

- never require sound for comprehension;
- respect system settings;
- keep haptics sparse and meaningful;
- no decorative audio loops in core product UI;
- urgent patterns must be reserved for genuinely urgent states;
- accessibility and device policy remain superior.

The Brand Pack defines the desired character; implementation remains platform-specific.

# 13. Brand Pack stage-awareness

This is the central integration contract.

## Stage 0 — Product / Project Truth authoring

**Brand Pack role:** identity feasibility and terminology reference only.

May contribute:

- existing brand-family names;
- brand identity implications;
- asset constraints;
- channel expression considerations.

Must not:

- create features;
- redefine products;
- alter business logic.

## Stage 1 — Development Unit / research seeding

**Brand Pack role:** publish a versioned `BrandContextReference` when the Unit is UI-bearing.

VEKL may research:

- relevant design techniques;
- accessibility;
- interaction patterns;
- current implementation approaches;
- product-specific visual references.

But the Brand Pack itself is not duplicated into each Unit.

The Unit references:

- brand release ID/hash;
- applicable product-expression profile ID;
- applicable application class;
- applicable brand intelligence domains.

## Stage 2 — Target resolution and Screen Registry × Feature Graph injection

**Brand Pack role:** none in deciding ownership.

After canonical screen/application/module resolution, the system may select the applicable Brand Pack projection.

The Brand Pack cannot add a screen because it wants a new composition.

## Stage 3 — Feature expansion / truth hydration

**Brand Pack role:** no domain facts.

It may specify presentation preferences for classes of data, but cannot satisfy missing truth.

## Stage 4 — Screen packet completeness

Brand information cannot turn an incomplete screen packet into a complete one.

Missing required product/domain truth still fails closed.

## Stage 5 — VEKL Design Authority / Product Experience

The development system compiles a `BrandContextProjection`:

```text
Brand Release
 + DIAL Global Identity
 + Product Expression Profile
 + Application Context
 + Screen-Role Context
 + Applicable Asset/Media Guidance
 + Applicable Interaction/Motion Intelligence
 + Applicable Brand Anti-Patterns
 + Applicable Critic Criteria
```

VEKL Product Experience combines that projection with:

- admitted design knowledge;
- donor applicability;
- anti-pattern knowledge;
- research evidence;
- freedom budget;
- current Product Experience route.

The Brand Pack does not replace VEKL knowledge.

## Stage 6 — EXPLORE visual generation

Brand Pack should be **high-intelligence, low-prescription**.

It contributes:

- identity anchors;
- composition principles;
- colour behaviour;
- art direction;
- typography character;
- product expression;
- screen-role tone;
- brand anti-patterns.

It should preserve creative latitude inside the existing freedom budget.

## Stage 7 — visual critique / convergence

Add a `BRAND_COHERENCE` critic dimension that evaluates:

- identity recognition;
- colour discipline;
- product-family coherence;
- product-context appropriateness;
- imagery/art-direction fit;
- over-branding / under-branding;
- accidental sub-brand drift.

It produces evidence. It does not promote authority.

## Stage 8 — Visual Authority freeze

Once Visual Authority is frozen, the Brand Pack can no longer be used as an excuse to redesign the approved composition.

Only:

- approved deltas;
- defect correction;
- authority-led revision

may change frozen visual dimensions.

## Stage 9 — Interaction & motion enrichment

Inject **Brand Motion Intelligence**, not a fixed motion script.

The interaction stage receives:

- frozen visual composition;
- real CapabilityEnvelope;
- Brand Motion Intelligence;
- product/application/screen context;
- reduced-motion/accessibility requirements.

It is free to author the best interaction solution inside those boundaries.

## Stage 10 — Interaction acceptance

Brand-specific acceptance checks are additive:

- interaction character fits DIAL;
- motion does not become decorative noise;
- product-specific motion metaphor is coherent;
- urgency semantics are not diluted;
- reduced-motion retains equivalent meaning.

All existing interaction, accessibility and performance gates remain superior.

## Stage 11 — Experience Authority freeze

The accepted interaction/motion solution becomes part of frozen Experience Authority.

Brand Pack no longer acts as a redesign source.

## Stage 12 — DDE productionization

Brand Pack contributes implementation assets and token projections only.

DDE must preserve Experience Authority.

No “brand cleanup” redesign is allowed during production binding.

## Stage 13 — parity certification

Brand verification checks:

- canonical brand release ID/hash;
- required brand anchors;
- token-source lineage;
- asset lineage;
- product-profile consistency;
- no forbidden colour/identity drift;
- visual and interaction parity with frozen authority.

## Stage 14 — learning

Accepted, evidenced design work may teach VEKL reusable design knowledge.

It does **not** mutate the Brand Pack automatically.

A repeated successful pattern may become a `BrandEvolutionCandidate`, but only owner/authorized brand authority can promote it into a later brand release.

# 14. Relationship with VEKL 2.2

VEKL 2.2 remains the development-knowledge topology.

Brand Pack integration obeys these rules:

1. no second graph authority;
2. no second capsule authority;
3. brand content is versioned and content-addressed;
4. UI-bearing Units carry Brand Pack references in Product Experience context;
5. VEKL may retrieve brand-relevant knowledge and research evidence;
6. a Brand Pack release is not Project Truth;
7. a VEKL finding cannot rewrite brand canon;
8. a Brand Pack rule cannot bypass VEKL qualification/admission;
9. stale brand-release references fail projection freshness checks;
10. accepted design learnings can propose brand evolution but not self-promote.

The seven existing VEKL context capsules remain intact. Brand context should be injected through the existing Product Experience projection/context rather than creating an eighth competing capsule.

# 15. Relationship with the Screen Registry × Feature Graph

The Brand Pack consumes, but never authors, the canonical graph.

It must support these lookup directions:

```text
screen_id
  -> module
  -> application(s)
  -> screen_kind / role
  -> applicable brand profile(s)

feature_id
  -> canonical screen(s)
  -> application(s)
  -> applicable brand profile(s)

application_id
  -> screen set
  -> product modules
  -> applicable brand expression context
```

Brand Pack projection is therefore **late-bound after screen/application resolution**.

This avoids stale duplicated screen mappings.

# 16. Relationship with frontend registries

## 16.1 FRONTEND_PRODUCT_PROFILE_REGISTRY

The Brand Pack is an upstream identity source for the existing product profiles.

It should enrich fields such as:

- `brand_character`;
- `visual_character`;
- `interaction_character`;
- brand release reference;
- media/art-direction profile;
- brand-motion profile.

It should not create a second profile resolver.

## 16.2 FRONTEND_TOKEN_REGISTRY

The current token registry remains the runtime frontend token authority.

The Brand Pack publishes DTCG-compatible **source tokens**.

A future projection/compiler maps approved Brand Pack tokens into the existing frontend registry.

Rules:

- no duplicated token IDs with divergent values;
- no hard-coded feature-level brand values;
- token lineage must be traceable to a brand release;
- product-specific overrides require an existing Product Design Profile;
- unresolved/unknown tokens fail closed under existing policy.

## 16.3 Component registry

The Brand Pack defines component **brand character**, not component identity or state ownership.

Examples:

- “primary action should have strong visual hierarchy” is brand guidance;
- `dial.action.primary` remains the component-registry authority.

## 16.4 Pattern policy

The Brand Pack may recommend contextual pattern tendencies.

It cannot silently allow a pattern forbidden by `FRONTEND_PATTERN_POLICY.json`.

## 16.5 Visual determinism

Brand releases and applicable profile hashes should be included in render/provenance envelopes so a later brand release cannot silently invalidate comparisons.

# 17. Brand Critic

The Brand Critic should be a structured evidence producer.

Suggested dimensions:

- `identity_recognition`
- `colour_discipline`
- `orange_selectivity`
- `dark_structure_quality`
- `typographic_character`
- `product_expression_fit`
- `application_context_fit`
- `imagery_art_direction_fit`
- `motion_character_fit`
- `cross_product_coherence`
- `accessibility_brand_integrity`
- `subbrand_drift`

Blocking examples:

- a product creates an unauthorized new brand palette;
- orange becomes a semantic error/success replacement;
- screen identity contradicts frozen Brand Pack law;
- Health uses consumer-campaign visual intensity on sensitive clinical workflows;
- operational safety surface uses decorative motion that obscures state;
- product profile is bypassed and `dial.global` is incorrectly used when a specific profile is known.

Non-blocking findings may include:

- orange density slightly high;
- hierarchy could rely more on dark structure;
- imagery feels generic;
- product personality is under-expressed.

The Brand Critic does not rank candidates by beauty on its own. It feeds the existing critic/convergence process.

# 18. Orange Budget Inspector

Orange-budget checking should be implemented as an assistive critic rather than a rigid percentage gate.

Signals:

- approximate orange surface share;
- strong orange focal-cluster count;
- number of orange CTAs;
- inactive orange controls;
- adjacent orange surfaces;
- orange use for semantic states;
- simultaneous hero + CTA + navigation saturation.

Default interpretation:

- ordinary UI: 3–7% is a useful target band;
- outside that band is not automatically wrong;
- deliberate acquisition/campaign surfaces may exceed it;
- checkout/safety/operational surfaces should usually be below it.

The final judgement must include screen role and design-zone context.

# 23. Development-stage anti-conflict rules

The following rules are mandatory.

1. **No screen duplication** — never author screen lists inside the Brand Pack.
2. **No feature duplication** — never restate Feature/FRC business semantics as brand truth.
3. **No domain facts** — examples cannot become data authority.
4. **No VEKL replacement** — Brand Pack is identity source, not knowledge graph.
5. **No eighth context-capsule authority** — project through Product Experience.
6. **No provider takeover** — Stitch remains the automatic frontend design provider under current policy.
7. **No frozen-authority redesign** — brand guidance cannot reopen approved Visual/Experience Authority.
8. **No pattern bypass** — Brand Pack cannot authorize patterns forbidden by frontend policy.
9. **No token fork** — approved identity tokens are projected into the existing token authority, not hard-coded elsewhere.
10. **No product sub-brand drift** — product profiles inherit DIAL global identity.
11. **No logistics module invention** — logistics remains an overlay/shared fulfilment expression unless Project Truth changes.
12. **No status-colour confusion** — semantic state remains separate from brand orange.
13. **No motion prescription collapse** — motion intelligence enriches the dedicated interaction/motion stage.
14. **No automatic brand learning** — accepted UI may propose evolution, not self-modify brand canon.
15. **No stale projection** — brand release/profile hash mismatch invalidates the projection.

# 24. Governance and release model

## 24.1 Release identity

Every published pack uses semantic versioning:

`dial-brand-pack@MAJOR.MINOR.PATCH`

Suggested semantics:

- MAJOR — identity law, core palette, logo or major product-expression break;
- MINOR — new product profile, new intelligence domain, additive asset family;
- PATCH — corrected guidance, metadata, non-breaking asset update.

## 24.2 Promotion

States:

```text
DRAFT
  ↓
REVIEWED
  ↓
OWNER_APPROVED / AUTHORIZED_BRAND_AUTHORITY
  ↓
CANONICAL_RELEASE
  ↓
SUPERSEDED or DEPRECATED
```

The development system should consume only releases allowed by policy.

## 24.3 Evolution from product work

Accepted product designs may create:

`BrandEvolutionCandidate`

A candidate contains:

- evidence refs;
- originating screen/product;
- repeated-success evidence;
- proposed generalization;
- conflicts;
- product-scope recommendation;
- owner decision requirement.

No candidate becomes brand truth automatically.

# 28. Final invariant

A DIAL frontend task must never receive “brand” as a free-floating style prompt.

It should receive a compiled, versioned, content-addressed brand projection that already knows:

- which DIAL product context applies;
- which application is being designed;
- which canonical screen is being designed;
- what role that screen plays;
- which brand laws are invariant;
- which expression dimensions are contextual;
- which visual/motion intelligence is useful;
- which brand anti-patterns apply;
- which authority layers remain superior;
- what has already been frozen and must no longer be redesigned.

The result is a Brand Pack that strengthens DIAL identity **without weakening the determinism, truth boundaries, creative intelligence or staged authority model of the existing DIAL development system**.
